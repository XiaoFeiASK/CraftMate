# CraftMate 交付计划

> 状态：v0.1 · 2026-11-02
> 目标：把当前 M0 骨架演进到「可连续直播一小时」的 M1，而不是一次性实现最后形态。

## 1. 当前基线

已经存在：

- `apps/admin-console`：React 管理端。
- `apps/desktop-shell`：Tauri 桌面宿主。
- `services/orchestrator`：本机 WebSocket 控制面。
- `packages/contracts`：观众事件、决策、控制面和 Bridge schema。
- `packages/agent`：确定性仲裁、人格、承诺状态机、场次读模型。

还没有：

- 持久化仓储和迁移执行器。
- 真实抖音接入。
- 模型调用与降级。
- TTS 和音频路由。
- Fabric Mod / 世界执行。
- 管理端的人格编辑、记忆和回放页面。

当前 `Show` 的决策、统计和承诺只在内存中，进程重启即丢失。下一阶段先把「可恢复的直播运行切片」做出来，再接外部世界。

## 2. 交付原则

1. **纵向切片优先**：每个 PR 必须有一条从输入到可观察结果的最小链路，不按「先写完所有仓储、再写所有接口」横切。
2. **契约先行**：跨进程或跨层的数据先进入 `packages/contracts`，再写实现。
3. **失败路径同批交付**：超时、非法输入、断线、重试至少有一条自动化测试；不把降级留到「稳定期」。
4. **先落库再出声**：承诺、动作、语音的状态变更必须能从数据库解释。
5. **一次只动一个可回滚理由**：一个 PR 应该能用一句话说明「为什么需要整体回滚」。
6. **不预埋空包**：目标目录可以写进文档，但不创建没有引用、没有测试的空模块。

## 3. 里程碑与 PR 切片

### M0.5 设计基线（本 PR）

交付：

- 本计划书。
- SQLite v1 DDL：证据、决策、承诺、动作、记忆、人格版本、待审、事件。
- DDL 可执行校验。
- 迁移与保留策略。

不做：

- 仓储实现。
- 运行时自动建库。
- 管理端新页面。
- 任何外部平台或模型调用。

验收：

- DDL 能在空库执行；`schema_migration` 表已定义版本和校验和列，写入由 M1.1 的迁移器实现。
- DDL 约束能拒绝非法状态和悬空外键。
- 当前决策、开放承诺、当前记忆视图可查询。
- `npm run db:check` 通过。

### M1.1 持久化闭环

交付：

- SQLite 连接、WAL、`busy_timeout`、迁移器。
- `Decision` 契约补 `priority` 字段（先改契约，再改仓储，避免 DDL 默认值掩盖）。
- `SourceStore`、`DecisionStore`、`CommitmentStore` 的最小接口和 SQLite 实现。
- `Show` 在仲裁前记录 source，在决策后记录 decision，在承诺变更时更新 commitment。
- 进程重启后仍能看到最近决策和未兑现承诺。

验收：

- 发送评论 → 重启 orchestrator → 管理端仍显示该决策。
- 承诺按 `reserve → speak → markSpoken` 顺序落库；跳过状态被拒绝。
- 每条决策同时保存优先级，供仲裁、语音队列和回放解释复用。
- 重复事件 ID 不会产生第二条 source。
- 数据库损坏或迁移失败时 orchestrator 明确退出，不静默降级。
- 原始评论超过 24 小时后只保留哈希和指标。

不做：

- 观众画像和长期记忆。
- 模型调用。
- 完整回放 UI。

### M1.2 评论接入

交付：

- `CommentSource` 的真实适配器边界和一个本机开发源。
- 去重、限流、断线重连、健康状态。
- 管理端显示接入状态与最近事件。

验收：

- 断开开发源后界面显示断线，重连后恢复。
- 重复 ID、空评论、超长评论、洪峰不会打崩 orchestrator。
- 重启后健康状态不会被伪造成「在线」。

不做：

- 抖音正式签名和风控全量实现；该适配器单独 PR。

### M1.3 模型决策

建议拆成两个 PR：

1. Provider 端口、超时、重试、结构化输出、错误分类。
2. Stage B/C 的分类与规划接入，模板降级，预算和延迟指标。

验收：

- 模型超时时 1 秒内仍能给出模板回应。
- 非法结构化输出不会触发执行。
- 每条决策能关联 provider、模型、耗时和最终决策。
- 观众文本仍只作为证据，不进入系统指令。

### M1.4 语音与字幕

建议拆成两个 PR：

1. `TtsProvider`、句子切分、播放队列、字幕同源。
2. 主备 TTS、熔断、音频路由和 OBS 联调。

验收：

- TTS 失败只降级为字幕，不阻断游戏动作。
- 抢占以短句为单位，不出现字符级硬切。
- 承诺在开口前已持久化。

### M1.5 游戏执行

建议拆成三个 PR：

1. Bridge 服务端和模拟 Mod 客户端，完成 `cmd/ack/result/event` 闭环。
2. Fabric Mod 骨架：连接、鉴权、能力协商、只读传感器。
3. 移动、挖掘、相机和按键看门狗。

验收：

- 一条指令走过去挖石头，切窗口不冻结。
- 断线 500ms 内释放按键。
- tick 线程没有文件、网络或数据库 I/O。

### M1.6 连续直播验收

这是集成 PR，不新增大功能：

- 1 小时本地直播彩排。
- 崩溃恢复、断线、模型超时、TTS 失败、操作员接管。
- 指标和回放抽查。

验收：

- 无人工重启完成 1 小时。
- 所有说出口的承诺都能在账本中解释。
- 任何一次接管都能正确回到 Agent 或 NONE。

## 4. 后续里程碑

### M2 记忆与人格

- 长期记忆、证据关联、召回预算。
- 人格版本、试听、对比和回滚。
- 待审队列与审批。
- 管理端记忆页和人格页。

建议每 1–2 个能力一个 PR，不把「记忆 + 人格 + 回放」塞进同一批。

### M3 稳定性与节目化

- 输出审查、披露分级。
- 回放时间轴。
- 投票、礼物优先级、镜头语言。
- 成本上限、预算告警。
- 4 小时稳定直播。

## 5. 什么时候创建 PR

### 可以直接创建 PR

- 一个可观察行为已经端到端成立，且测试覆盖主路径和至少一个失败路径。
- 一个契约变更已经同时更新生产代码、消费方和契约测试。
- 一个迁移可以执行、可回滚到上一版数据库（前向修复或恢复备份），并有校验。
- 纯设计变更已经能让另一位工程师据此实现，且没有未决的阻塞问题。

### 应该先开 Draft PR

- 跨两个以上包的接口需要早期评审，但实现尚未完成。
- 迁移会改变已有数据，需要先确认回填和保留策略。
- 需要产品拍板（例如真实的抖音接入方式），但代码骨架可以先评审。

Draft PR 只能用于「接口和边界已稳定」，不能用来代替设计文档。

### 不应该创建 PR

- 只有目录、空文件或 TODO，没有行为、测试或可评审设计。
- 主路径跑不通，靠注释说明「后续补」。
- 把多个互不相关的重构塞进同一个 PR。
- 迁移没有在空库和已有数据副本上验证。

### PR 大小

目标：

- 业务代码变更小于 400 行（不含移动、锁文件、生成物、文档）。
- 最多触及 2 个运行时包；超过时先拆契约 PR 和实现 PR。
- 一个 PR 只解决一个主要问题；文件移动可以单独成 PR。

超过时不是硬性拒绝，但必须在描述里解释为什么不能拆。

## 6. 每个 PR 的完成定义

必须满足：

- `npm run typecheck` 通过。
- `npm test` 通过。
- `npm run build` 通过。
- 涉及 DDL 时，`npm run db:check` 通过。
- 涉及持久化时，验证 WAL、外键和 `busy_timeout` 在真实文件库启用。
- 新增错误路径有测试或可复现步骤。
- 公开契约变化已同步 `packages/contracts` 和文档。
- 没有静默空操作；未实现的能力明确禁用或返回错误。
- 数据库变更包含迁移、索引、保留策略和失败处理。

建议在 PR 描述中写：

```text
行为：用户能观察到什么
边界：本 PR 不做什么
数据：是否有迁移，如何验证
失败：超时、非法输入、断线时发生什么
回滚：如何撤回
```

## 7. 分支与提交

- 分支：`fix/<slice-name>` 或 `feat/<slice-name>`。
- 提交按「契约 / 实现 / 文档」可分开，但一个 PR 内保持同一目标。
- 不把生成物、`dist/`、本地数据库或日志提交进仓库。
- 推送前确认 `origin` 指向 `XiaoFeiASK/CraftMate`。

## 8. 风险与停止条件

出现以下情况时暂停扩展功能，先修基础：

- 迁移无法在已有数据上重复验证。
- 重启后决策、承诺或模式不一致。
- 同一事件被重复执行。
- 承诺先出声后落库。
- 观众文本进入系统提示。
- tick 线程出现阻塞 I/O。

这些是架构不变量，不是「稳定性阶段的优化项」。

## 9. 排期（Deadline）

### 9.1 排期假设

先写明假设，否则日期没有意义：

- 1 名主要开发者，全职投入时按每周 1 个里程碑切片推进。
- 业余投入（每周约 8 小时有效开发）时，所有日期乘以 2。
- 不包含抖音正式接入资质、OBS 现场联调、美术和音色采购的等待时间。
- 每个日期都是「该 PR 可评审」的日期，不是「功能完美」的日期。

### 9.2 如果延期，按这个顺序砍

砍功能，不砍验收：

1. 先砍 M1.4b 主备 TTS（单 TTS + 字幕降级仍可直播）。
2. 再砍 M1.3b 的 Stage C 规划，只保留分类 + 模板回应。
3. 再砍 M1.5c 的挖掘，只保留移动和相机。
4. 不砍 M1.1、M1.6 和失败路径测试。没有持久化和 1 小时验收，后面全是演示。

### 9.3 设计到什么程度就该开 PR

判断标准是「另一位工程师能否只读这个 PR 就接着写」，不是「设计是否想全」。

| 设计完成度 | 动作 |
| --- | --- |
| 只有目录、命名和分层想法 | 不建 PR，留在 issue 或设计文档草稿。 |
| 契约（schema / 消息 / 表）已定，实现未开始，且跨 2 个以上包 | 开 **Draft PR**，先评审边界。 |
| 契约已定 + 一条主路径能跑通 + 一个失败路径有测试 | 开 **正式 PR**。 |
| 只差 UI 细节、文案、非关键指标 | 开正式 PR，把细节列进描述，不阻塞合并。 |

具体到本项目：

- **M0.5（当前）**：设计文档 + DDL + 校验脚本已自洽，可以直接开正式 PR。理由是 DDL 可执行、约束被测试覆盖，不依赖未实现代码。
- **M1.1a**：迁移器接口和 `schema_migration` 写入规则定了就开 Draft；能重复执行两次且校验和不匹配会拒绝时转正式。
- **M1.1b**：必须等到「发评论 → 重启 → 仍能看到决策」这条路径手工跑通才开正式 PR。
- **M1.3 / M1.4 / M1.5**：每个内部拆分的第一个 PR 都是契约或骨架，用 Draft；第二个 PR 起走正式。

硬性红线：只要出现下面任意一条，就不开 PR。

- 主路径需要口头解释才能跑通。
- 会改动已有数据的迁移，只在内存库验证过，没在文件库和已有数据副本上跑过。
  （M0.5 的 `0001_initial.sql` 是全新空库迁移，`db:check` 在内存库验证即可；
  文件库 + 备份恢复验证从 M1.1a 开始成为硬要求。）
- 新增表或字段没有对应的 `db:check` 断言。
- PR 描述里出现「后续补」「暂时跳过」「先这样」而没有对应 issue。

### 9.4 每个 PR 的时间盒

- 设计类 PR：2 天内必须能评审，否则说明范围太大。
- 实现类 PR：5 个工作日内必须能评审，否则拆。
- 超过时间盒不是延期理由，是拆分信号。
