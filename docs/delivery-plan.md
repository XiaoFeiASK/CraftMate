# 交付计划

> 目标：把当前骨架演进到「可连续直播一小时」，一个一个切片做，不一次性实现最后形态。
> 「现在能跑什么」见 [实现状态](status.md)；架构约束见 [架构纵览](architecture.md)。

## 1. 基线

已存在：React 管理端、Tauri 宿主、Orchestrator 控制面与 `/ingress`、Ingress 接入端、Agent 确定性仲裁与承诺状态机、共享契约、SQLite schema、持久化 Store。

还不存在：真实抖音房间联调、模型调用、TTS、Bridge 服务、Fabric Mod、人格编辑 / 记忆 / 回放页面。

当前 `Show` 的承诺仍只在内存；决策与证据已可落库；Ingress 与 `sourceHealth` 链路已通，但没有自动化测试。下一阶段的重点是把「可恢复的直播运行切片」补完，再接外部世界。

## 2. 交付原则

1. **纵向切片优先**：每个 PR 必须有一条从输入到可观察结果的最小链路，不横切「先写完所有仓储」。
2. **契约先行**：跨进程或跨层的数据先进入 `packages/contracts`，再写实现。
3. **失败路径同批交付**：超时、非法输入、断线、重试至少有一条自动化测试。
4. **先落库再出声**：承诺、动作、语音的状态变更必须能从数据库解释。
5. **一次只动一个可回滚理由**：一个 PR 应该能用一句话说明「为什么需要整体回滚」。
6. **不预埋空包**：目标目录可以写进文档，但不创建没有引用、没有测试的空模块。

## 4. 当前：M1 闭环

### M1.1 持久化闭环

已落地：迁移器、`SessionStore`、`SourceStore`、`DecisionStore`、`ActionStore`、启动恢复、事件去重、`Decision.priority` / `skill` 契约。

剩余交付：

- 承诺状态迁移落库（`commitment` / `commitment_event`）。
- `packages/storage` 自动化测试：空库建库、重复迁移、checksum 漂移、重复事件、幂等动作。
- 保留策略定时任务调用 `expireRawText()`，并写审计记录。
- 删除内存 `Show.seen` 与数据库去重的重复职责，明确唯一裁决方。

验收：

- 删库 → 启动 → 表存在；再启动 → 迁移表不新增。
- 发评论 → 重启 → 控制台仍显示该决策。
- 同一 `external_event_id` 发两次 → `source` 只有一行。
- 承诺按 `reserve → speak → markSpoken` 顺序落库；跳过状态被拒绝。
- 数据库损坏或迁移失败时 Orchestrator 明确退出，不静默降级。

不做：长期记忆、模型调用、回放 UI。

### M1.2 评论接入

已落地：`services/ingress` 的 dyhub 适配、归一化、去重限流、上报缓冲，Orchestrator 的 `/ingress` 握手、事件接收与 `source` 广播。

剩余交付：

- `/ingress` 增加独立 token 与拒绝非本机来源。
- 管理端把接入状态接到界面上（契约与广播已就绪）。
- 假 dyhub 的端到端测试：连接、断线、房间关闭、洪峰。

验收：

- 测试内起假 dyhub → 事件进入 `Show.ingest` → 控制台出现决策。
- 停掉 dyhub → 3 秒内界面变「断线」；恢复 → 自动重连并标「在线」。
- `roomStatus: closed` 不产生假评论。
- 一秒 200 条洪峰 → 不 OOM，丢弃计数可见。

不做：官方开放平台、多房间、礼物登录态。

已知限制：游客态拿不到礼物事件，需要 `DYHUB_COOKIE`。首版接受「礼物缺失」，但决策里不出现伪造的礼物加权。

### M1.3 模型规划

建议拆成两个 PR：

1. Provider 端口、超时、重试、结构化输出、错误分类。
2. Stage B/C 接入、模板降级、预算与延迟指标。

验收：

- 注入永不返回的 Provider → 1 秒内出模板决策。
- 注入坏 JSON → 拒绝执行，记 incident，不产生 `action_attempt`。
- 每条决策能关联 provider、模型、耗时。
- 观众文本不出现在系统提示里（检查 prompt 组装函数入参）。

不做：多 Provider 路由、embedding、人格微调。

### M1.4 语音与字幕

建议拆成两个 PR：

1. `TtsProvider`、句子切分、播放队列、字幕同源。
2. 主备 TTS、熔断、音频路由与 OBS 联调。

验收：

- TTS 失败只降级为字幕，不阻断游戏动作。
- 抢占以短句为单位，不出现字符级硬切。
- 承诺在开口前已持久化。

不做：专属音色克隆（授权约束见 [D-13](decisions.md#d-13)）。

### M1.5 游戏执行

建议拆成三个 PR：

1. `/bridge` 服务端 + 模拟 Mod：`hello` / `cmd` / `ack` / `progress` / `result` / `cancel` / `event`，含看门狗、幂等键、队列上限。
2. MCP Fabric 适配器：`packages/bridge-mcpfabric`，技能映射见 [外部接入](integration.md) §3.2。开工前先做 2 小时可用性验证。
3. Fabric Mod 骨架：连接、鉴权、能力协商、只读传感器，再补移动、挖掘、相机、按键看门狗。

验收：

- 模拟客户端跑通 `cmd → ack → progress → result`。
- 重复 `idempotencyKey` 只执行一次。
- 断开 500ms 内发出 `cancel`，未完成动作记 `cancelled` 而非 `failed`。
- 真游戏中一条指令走过去挖石头，切窗口不冻结。
- tick 线程没有文件、网络或数据库 I/O。

不做：把 mcpfabric 当发行依赖；多账号。

### M1.6 连续直播验收

集成 PR，不新增大功能：

- 1 小时本地直播彩排。
- 崩溃恢复、断线、模型超时、TTS 失败、操作员接管。
- 指标与回放抽查。

验收：

- 无人工重启完成 1 小时。
- 所有说出口的承诺都能在账本中解释。
- 任何一次接管都能正确回到 Agent 或 NONE。

## 7. PR 与完成定义

### 7.1 什么时候创建 PR

可以直接创建：

- 一个可观察行为端到端成立，测试覆盖主路径和至少一个失败路径。
- 一个契约变更已同时更新生产代码、消费方和契约测试。
- 一个迁移可执行、可回滚（前向修复或恢复备份），并有校验。
- 纯设计变更已能让另一位工程师据此实现，且没有未决的阻塞问题。

应该先开 Draft：

- 跨两个以上包的接口需要早期评审，但实现尚未完成。
- 迁移会改变已有数据，需要先确认回填和保留策略。
- 需要产品拍板（例如抖音接入方式），但代码骨架可以先评审。

Draft PR 只能用于「接口和边界已稳定」，不能代替设计文档。

不应该创建：

- 只有目录、空文件或 TODO，没有行为、测试或可评审设计。
- 主路径跑不通，靠注释说明「后续补」。
- 把多个互不相关的重构塞进同一个 PR。
- 迁移没有在空库和已有数据副本上验证。

### 7.2 大小与完成定义

- 业务代码变更小于 400 行（不含移动、锁文件、生成物、文档）。
- 最多触及 2 个运行时包；超过时先拆契约 PR 和实现 PR。
- 一个 PR 只解决一个主要问题；文件移动可以单独成 PR。

每个 PR 必须满足：

- `npm run typecheck`、`npm test`、`npm run build` 通过。
- 涉及 DDL 时，`npm run db:check` 通过；涉及连接或迁移时额外跑 `db:check:file`。
- 新增错误路径有测试或可复现步骤。
- 公开契约变化已同步 `packages/contracts` 和文档。
- 没有静默空操作；未实现的能力明确禁用或返回错误。

PR 描述模板：

```text
行为：用户能观察到什么
边界：本 PR 不做什么
数据：是否有迁移，如何验证
失败：超时、非法输入、断线时发生什么
回滚：如何撤回
```

### 7.3 分支与提交

- 分支：`feat/<slice-name>` 或 `fix/<slice-name>`。
- 提交按「契约 / 实现 / 文档」可分开，但一个 PR 内保持同一目标。
- 不提交生成物、`dist/`、本地数据库或日志。
- 推送前确认 `origin` 指向 `XiaoFeiASK/CraftMate`；未经确认不推送。

## 8. 风险与停止条件

出现以下情况时暂停扩展功能，先修基础：

- 迁移无法在已有数据上重复验证。
- 重启后决策、承诺或模式不一致。
- 同一事件被重复执行。
- 承诺先出声后落库。
- 观众文本进入系统提示。
- tick 线程出现阻塞 I/O。

这些是架构不变量，不是「稳定性阶段的优化项」。

### 时间盒

不排日程，但单个 PR 有时间盒：设计类 2 天内必须能评审，实现类 5 个工作日内必须能评审。超时不是延期理由，是拆分信号。
