# 技术选型

> 一句话：**前端 Tauri + React + TypeScript，后端 Node 22 + TypeScript，游戏侧 Java 21 + Fabric。**
> 这不是「哪个语言最强」的比较，而是「这个项目的负载长什么样」的比较。

## 0. 先看负载

这个系统的时间花在哪：

| 工作 | 时间占比 | 性质 |
| --- | --- | --- |
| 等模型 API 返回 | ~50% | I/O 等待 |
| 等 TTS 合成 | ~15% | I/O 等待 |
| 等游戏动作完成 | ~25% | I/O 等待 |
| 仲裁打分、状态机推进 | ~8% | 微秒级计算 |
| 序列化、校验 JSON | ~2% | 轻量计算 |

**结论：这是 I/O 编排密集型系统，不是计算密集型系统。**

真正的 CPU 热点（寻路 A*、区块解析、实体追踪）全部在 Minecraft Mod 里，用 Java 写，不在后端。所以后端语言的"性能"不是第一优先级，开发效率、生态、类型一致性才是。

## 1. 一张总表

| 层 | 选型 | 一句话理由 |
| --- | --- | --- |
| 管理端前端 | Tauri 2 + React + TypeScript | 原生窗口 + Web 渲染效率，单人可维护 |
| 后端 / 执行内核 | Node 22 + TypeScript | 全链路同语言同类型，模型生态最全 |
| 游戏执行 | Java 21 + Fabric | 没有选择：Mod 只能跑在 JVM 上 |
| 数据存储 | SQLite（WAL + FTS5） | 单机单进程，无需服务端数据库 |
| 语音 | Node + ffmpeg + 云 TTS | 流式合成与混音，链路简单 |
| 模型 | DeepSeek（OpenAI 兼容） | 中文口语好、成本低、人格同源 |
| 推流 | OBS + obs-websocket | 成熟，可脚本控制 |

## 2. 前端：为什么是 Tauri + React

### 2.1 为什么不用 Electron

Electron 能用，但代价是：

- 每个窗口一个 Chromium，内存 200MB 起步。
- 打包体积 150MB+。
- 和系统托盘、全局快捷键、权限的集成要额外写。

Tauri 用系统 WebView（macOS 是 WKWebView），同样写 React，但：

- 安装包 10MB 级。
- 内存占用低一个量级。
- 原生窗口、托盘、菜单、全局快捷键是框架自带能力。
- 后端可以用 Rust 写，也可以直接调本机 Node sidecar。

对一个同时跑 Minecraft + OBS 的 Mac 来说，省下的 300–500MB 内存是实打实的。

### 2.2 为什么不选纯原生（Qt / Avalonia / SwiftUI）

| 方案 | 优点 | 为什么没选 |
| --- | --- | --- |
| SwiftUI | macOS 体验最好 | 不能跨 Windows，后面要重写 |
| Qt / QML | 跨平台、性能好 | C++/QML 与 TS 后端跨语言，单人维护成本高 |
| Avalonia（.NET） | 跨平台、原生感好 | 同样跨语言，且桌面生态不如 Web |
| Tauri | 跨平台、体积小、TS 全栈 | 渲染仍是 Web 技术 |

用户要求"不要 Web 那种 UI"，这指的是**交互形态**，不是排斥渲染技术。Tauri 完全可以做出原生感：系统标题栏、菜单栏、托盘、`Cmd+K`、多面板固定布局、无地址栏无标签页。

当前界面按 Launcher 启动器来做：自绘标题栏、账户区、分组导航、全幅场景、同窗操作抽屉。它不是把管理后台套进一个窗口，也不会暴露地址栏、标签页或网页式多级导航。如果未来明确要求"连渲染层也不能是 Web"，再换 Avalonia，代价是前后端两套语言。

### 2.3 为什么是 React 不是 Vue / Svelte

三个都能做。选 React 的理由只有一条：**生态和 AI 辅助生成的成熟度最高**，复杂状态面板（决策流、时间轴回放、可拖拽分栏）现成方案最多。这不是技术优劣，是维护成本。

## 3. 后端：为什么是 Node + TypeScript

### 3.1 四个端共享一套类型

```text
Console ─┐
Ingress ─┼─ 同一套 zod schema ─ 同一套 TS 类型
Voice   ─┤
Kernel  ─┘
```

改一个字段，四处同时报错或同时通过。这是跨语言方案做不到的：Go 或 Python 都要额外维护 protobuf / JSON Schema / codegen，最容易出的线上事故就是"字段漂移"。

模型 function calling 的 schema 也可以直接由 zod 生成，不用维护两份定义。

### 3.2 模型生态最成熟

这个项目重度依赖：

- 流式 token
- 结构化输出 / JSON mode
- function calling
- 多 Provider 切换
- 超时、重试、计费统计

TypeScript 侧这些基本开箱即用，且新能力跟进最快。DeepSeek 本身提供 OpenAI 兼容接口，TS SDK 直接用。

### 3.3 单线程事件循环反而合适

系统天然是「大量并发等待 + 少量状态变更」：

- 等模型、等游戏、等 TTS 都是 Promise。
- 仲裁器读写共享状态时没有锁的问题。
- 不需要处理数据竞争。

Go 里要么加锁，要么把状态塞进单个 goroutine 用 channel 串行化——后者本质就是"用 Go 模拟 Node"。

### 3.4 代价要说清楚

- **取消是协作式的**：任何异步入口忘了传 `signal`，就会悬挂。必须靠规范 + 审计。
- **未捕获异常可能带走进程**：需要守护进程 + `unhandledRejection` 处理。
- **内存比 Go 高**：每个 Node 进程 80–200MB。
- **CPU 密集任务会阻塞**：所以寻路、区块解析必须放 Mod，不能放 Node。

## 4. 为什么不用 Python

Python 在 AI 领域很强，但这个项目的 AI 是"调 API"，不是"跑模型"。

| 维度 | Python | 本项目需要 |
| --- | --- | --- |
| 模型推理 | 强 | 不需要，推理在云端 |
| AI 库生态 | 最强 | 只用 HTTP SDK |
| 异步并发 | asyncio 可用，但生态割裂 | 需要统一异步链路 |
| 类型系统 | 需 mypy，运行时无强制 | 要在四端共享运行时校验 |
| 打包桌面 | 麻烦（PyInstaller 体积大、杀软误报） | 需要轻量桌面程序 |
| 与前端共享类型 | 跨语言，需 codegen | 希望零成本共享 |

具体问题：

1. **没有真正的运行时类型**。zod 在 TS 里既是类型又是运行时校验；Python 的 Pydantic 能做，但跨语言给前端用还要导出 JSON Schema。
2. **打包和分发**。PyInstaller 产物几十到上百 MB，macOS 签名、公证、杀软误报都更麻烦。
3. **异步生态不统一**。同步库和 async 库混用是常见的坑，尤其 TTS、音频、WebSocket 三条链路。
4. **进程模型更重**。四五个 Python 进程常驻，内存和启动时间都不占优。

**Python 仍然适合的地方**（明确保留）：

- 离线数据分析：直播复盘、决策分布统计。
- 模型效果实验：prompt A/B、人格评测。
- 一次性脚本：素材处理、字幕校对。

这些不进主运行链路，用什么语言都行。

## 5. 为什么不用 Go

Go 的真实优势，我不掩饰：

| 优势 | 说明 |
| --- | --- |
| `context.Context` | 取消是语言级公民，贯穿全链路，比 Node 可靠 |
| goroutine 隔离 | 单请求 panic 可 recover，不带崩进程 |
| 单二进制 | 15–25MB，无运行时依赖，部署简单 |
| 内存 | 常驻 30–80MB，比 Node 低 |
| 高并发 | WebSocket、protobuf 场景更从容 |
| 可预测性 | GC 停顿可控，pprof 成熟 |

那为什么还是不用？

### 5.1 多一层跨语言边界

前端要 TS，Mod 是 Java。如果后端用 Go，系统就变成三种语言 + 两套协议 + 两套 codegen。**边界数量是复杂度的乘数。**

### 5.2 类型无法共享

Go 的结构体不能直接给 React 用。要么维护 protobuf，要么维护 JSON Schema + 双向生成。改一个字段要跑一次 generate，忘了就漂移。

### 5.3 模型 SDK 滞后

Go 的 LLM SDK 普遍比 TS 慢半拍。流式、function calling、结构化输出的边角问题更常见，很多要自己拼 HTTP。

### 5.4 开发速度

MVP 阶段最大的成本是改需求，不是跑不动。TS 改字段、热重载、直接读 JSON，比 Go 的结构体 + 接口 + 错误处理样板快。

### 5.5 取消语义是唯一真正羡慕的地方

Go 的 context 确实更适合这个系统。但 Node 用 `AbortController` 也能做到，只要规范到位。这是"工程纪律"问题，不是"语言做不到"。

### 5.6 什么情况下改 Go

给出可量化条件，不靠感觉：

- 同时托管 3 台以上游戏实例。
- 评论吞吐持续超过 1000 条/秒。
- 内核 p99 调度延迟超过 200ms，且 profiling 证明瓶颈在运行时。
- 需要对外提供 SDK，要求单二进制分发。

当前是单直播间、单实例，不会触发。真正先成为瓶颈的是 Mod 的寻路和 tick，不是后端语言。

## 6. 游戏侧：为什么只能 Java

没有选择。Fabric Mod 跑在 JVM 上，Mixin 直接改字节码，必须用 Java（或 Kotlin 编译到 JVM）。

选 Java 21 而不是 Kotlin 的理由：

- Fabric 官方模板、Mixin 示例、社区源码都是 Java。
- Kotlin 会多一层编译和映射问题，在这个版本敏感的场景里不划算。
- 只有一个人写 Mod 时，少一层抽象就是少一类 bug。

## 7. 数据：为什么是 SQLite

- 单机、单用户、单进程写入，不需要服务端数据库。
- WAL 模式下读写并发够用。
- FTS5 做记忆检索，不需要额外部署向量库。
- 整个数据库就是一个文件，备份和迁移简单。

规模上来（几万条记忆、需要混合检索）再加向量库或独立服务，不影响上层接口。

## 8. 决策矩阵

| 维度 | Node/TS | Python | Go |
| --- | --- | --- | --- |
| 与前端共享类型 | 极好 | 差 | 差 |
| 模型生态 | 最好 | 好 | 一般 |
| 取消/超时 | 协作式 | 弱 | 最好 |
| 故障隔离 | 弱 | 中 | 好 |
| 单线程并发安全 | 无锁 | GIL 限制 | 需锁 |
| 内存占用 | 高 | 中 | 低 |
| 桌面打包 | 好 | 差 | 好 |
| 开发速度 | 快 | 快 | 中 |
| 单二进制分发 | 需 SEA/Bun | 差 | 最好 |

在这个项目的权重下（类型共享、模型生态、开发速度优先），TS 得分最高。

## 9. 一句话总结

- **前端**：Tauri 拿原生外壳，React 拿开发效率，两者都不牺牲"像本地程序"的体验。
- **后端**：Node 不是性能最好的，但它是让四个端用同一种语言说话的方案，而在这个 I/O 密集的系统里，这比 CPU 性能值钱。
- **Python**：留在数据分析和实验环节，不进主链路。
- **Go**：等真的出现高并发多实例需求再上，现在上是提前优化。
- **Java**：Mod 的硬约束，没有替代。
