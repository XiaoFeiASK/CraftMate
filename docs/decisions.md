<a id="d-01"></a>
## D-01 游戏执行层用 Fabric Mod，不用 Mineflayer

**状态**：已采纳 · 2026-11-02

**背景**：最初计划用 Mineflayer 做 MVP，接入快、纯 JS、可与内核同语言。用户确认已见过成熟的 Fabric Mod + WebSocket 玩法。

**选择**：直接采用 Fabric 客户端 Mod + 本机 WebSocket Bridge。

**理由**：

- 客户端 Mod 有完整相机、手部动作、HUD、受伤反馈，Mineflayer 基本没有。
- 复杂建造、战斗、原版 UI 交互在 Mineflayer 上受限。
- 执行循环放在 Mod 内，延迟从每步一次往返降到每个任务一次下发。
- 方案已被外部玩法验证，不必再付一次迁移成本。

**后果**：多一个 Java 进程、一套 Gradle 构建和 Mixin 维护成本；版本升级成本更高，需要 D-06 的 compat 层。

**已废止的方案**：MVP 用 Mineflayer 验证，之后再换 Fabric。

<a id="d-02"></a>
## D-02 执行内核用 TypeScript，不用 Go

**状态**：已采纳 · 2026-11-02

**背景**：Node/TypeScript 与 Go 都可行，需要判断哪个更适合「大量 I/O 等待 + 少量状态变更」的编排系统。

**选择**：执行内核、接入端、语音、管理端统一用 TypeScript。

**理由**：

- 四端共享一套类型与 zod schema，改字段不需要跨语言 codegen。
- 模型生态最成熟：流式、function calling、结构化输出、多 Provider。
- 单线程事件循环让仲裁器无锁，快速迭代期价值高。
- 真正的 CPU 热点（寻路、区块解析）在 Mod 里，不在内核。

**后果**：取消是协作式的，必须规范所有异步入口传 signal；未捕获异常可能带走整个进程，需要守护进程兜底；内存和打包体积高于 Go。

**重新评估条件**：同时托管 3 台以上实例、评论吞吐持续超过 1000 条/秒、内核 p99 调度延迟超过 200ms 且瓶颈在运行时、或需要单二进制 SDK 分发。

<a id="d-03"></a>
## D-03 客户端 Mod 驱动真实玩家账号

**状态**：已采纳 · 2026-11-02

**背景**：游戏执行有服务端假玩家、客户端 Mod 驱动真实账号、双端 Mod 三种形态。用户已有专用账号，并要求 Agent 直接操作该账号。

**选择**：Fabric 客户端 Mod 直接驱动真实玩家账号的输入层，不造 NPC。

**理由**：账号本身就是 Agent 的身体，画面即直播画面；相机、动画、HUD 都在客户端；不需要 OS 级键鼠模拟，不抢焦点。

**后果**：一个账号只有一个身体，人和 Agent 不能同时操作，必须有控制权三态；WS 断开必须释放所有按键；自动化只允许在自有存档或授权服务器中使用。

<a id="d-04"></a>
## D-04 本地单人世界作为直播场地

**状态**：已采纳 · 2026-11-02

**背景**：候选是自建 Fabric 服务器与本地单人世界。用户确认使用本地单人世界，并新建直播存档。

**选择**：直播运行在本地单人世界，不部署服务端 Mod，不做多人规则，不做反作弊。

**理由**：没有跨进程通信，Mod 直接拿权威状态；部署链路最短；新建存档可按节目需要选择地形和初始资源。

**后果**：必须关闭「失焦暂停」（`pauseOnLostFocus:false`），否则切窗口会冻结游戏；世界和存档在直播机上，需要本机备份；未来做多人或无人值守需重新评估。

<a id="d-05"></a>
## D-05 管理端用 Tauri，交互按原生桌面程序做

**状态**：已采纳 · 2026-11-02

**背景**：用户明确不要「Web 那种 UI」，要类似本地程序的形态。单人团队需要管理端与内核共享类型。

**选择**：Tauri 2 + React + TypeScript。渲染技术是 Web，交互形态必须按原生桌面程序设计。

**约束**：系统标题栏、菜单栏、托盘、Dock 图标；无地址栏、无标签页、无卡片瀑布流；固定多面板、可拖拽分栏、`Cmd+K` 命令面板；关闭窗口隐藏而不是退出；多显示器位置记忆。

**后果**：若「不要 Web」被解释为禁止 Web 渲染，需改 Avalonia 或 Qt，代价是跨语言和更慢迭代；推流画面不能使用管理端窗口，必须由 OBS 直接采集游戏。

<a id="d-06"></a>
## D-06 版本不锁死，用 compat 层隔离差异

**状态**：已采纳 · 2026-11-02

**背景**：用户表示版本不需要锁死，1.2x 都可以切换。但 Mod 的 Mixin 与映射对版本高度敏感。

**选择**：当前基线 1.21.11。Mod 分 `core` / `api` / `compat` 三层，版本相关代码只放 `compat`。

**约束**：

1. `core` 不出现任何 Minecraft 类型。
2. 协议只出现语义 ID、整数坐标、tick。
3. `fabric.mod.json` 只声明实测过的版本范围。

**后果**：换版本时新增 `compat/vX_X_X`，内核与协议不变；不在未测试版本上宣称支持；同一时间只维护一个兼容目标。

<a id="d-07"></a>
## D-07 抖音接入做官方与抓取双实现

**状态**：已采纳 · 2026-11-02

**背景**：抖音是首发平台。官方直播互动能力需要资质与审核；第三方抓取不稳定但开发期可用。

**选择**：定义 `CommentSource` 接口，提供 `douyin-official` 与 `douyin-capture` 两个实现，上层只依赖 `AudienceEvent`。

**理由**：审核周期不受开发控制，不能阻塞开发；抓取可早早在真实弹幕流联调；平台差异必须隔离在接入端。

**后果**：抓取实现需自行处理签名刷新、重连、风控；正式上线优先切官方；换平台只新增适配器。

<a id="d-08"></a>
## D-08 不复制 AGPL 项目代码

**状态**：已采纳 · 2026-11-02

**背景**：AstrBot 是 AGPL-3.0，工程结构和安全流水线有参考价值。项目可能需要闭源或商业化。

**选择**：AstrBot 只作为设计参考，不复制代码、不 fork、不做进程内链接。

**可借鉴**：流水线阶段顺序；StrategySelector 的可插拔策略结构；输入与输出共用同一个审查入口；TTS Provider 清单。

**后果**：所有借鉴点必须独立重写；如确需复用，只能走独立进程 + HTTP 边界，并需律师判断是否构成衍生作品；评审时把来源检查纳入清单。

<a id="d-09"></a>
## D-09 默认人格用社区大肥鱼

**状态**：已采纳 · 2026-11-02

**背景**：用户希望使用社区流行的 DeepSeek 大肥鱼形象，但性格偏软萌，不要毒舌。

**选择**：默认人格为大肥鱼：软萌、爱撒娇、贪吃、爱面子、偶尔嘴硬但心软；知道自己是大肥鱼并为此骄傲。权重上降低 `sass`，保留 `gluttony`。

**身份声明**：大肥鱼是 DeepSeek 蓝鲸 logo 的社区二创形象，不是官方角色。项目不冒充官方，也不分发角色美术资源。

**后果**：人格是结构化对象，`weights` 进入仲裁而不只是语气；音色、立绘、二创素材的商用授权需单独确认；人格修改走版本链，可回滚。

<a id="d-10"></a>
## D-10 双许可 MIT OR Apache-2.0

**状态**：已采纳 · 2026-11-02

**背景**：用户要求许可证与 SeekMemory 一致，后者采用 MIT 或 Apache-2.0 双许可。

**选择**：`MIT OR Apache-2.0`，使用者可任选其一，完整文本放 `licenses/`。

**后果**：根目录不出现许可证文件；GitHub 不会自动识别许可证徽标，需要在 README 说明；第三方依赖许可证仍需单独核对，特别是 LGPL 的 Baritone。

<a id="d-11"></a>
## D-11 暂不做完整风险分级与存档回滚

**状态**：已采纳 · 2026-11-02

**背景**：早期设计包含红黄绿动作分级、存档快照、整盘回滚、事故恢复流程。用户明确表示这些属于过度设计。

**选择**：当前只保留三处必要机制：Mod 内安全反射、操作员接管、急停。

**不做**：动作风险分级表、自动存档快照、回滚策略、事故复盘流水线。

**后果**：M0–M1 范围显著缩小；若后续引入高风险玩法或多人环境，需重新提出决策，而不是默认已有方案。

<a id="d-12"></a>
## D-12 模型接入先用 DeepSeek

**状态**：已采纳 · 2026-11-02

**背景**：需要分层使用模型：Stage B 分类打分、Stage C 规划、台词生成。

**选择**：第一阶段统一走 DeepSeek，通过 OpenAI 兼容协议接入。Stage B 与台词用 `deepseek-chat`，Stage C 用 `deepseek-reasoner`。

**理由**：人格设定本身就是 DeepSeek 生态的大肥鱼，模型与角色来源一致；中文口语化质量好、成本低；OpenAI 兼容协议让换供应商只改 baseURL 和 model。

**后果**：结构化输出稳定性需实测，必要时用 JSON 模式加本地校验兜底；推理模型延迟高，必须「先说话后执行」；API Key 存 Keychain，按 Key 独立预算与限速。

<a id="d-13"></a>
## D-13 语音参考社区大肥鱼音色

**状态**：已采纳 · 2026-11-02

**背景**：人格已经确定为社区大肥鱼。语音是角色辨识度的一半，音色不一致会让观众出戏。

**选择**：音色以社区公开的大肥鱼语音为参考目标。先用云厂商现成音色做近似，链路稳定后再评估专属克隆。

**顺序**：火山引擎现成中文女声（调高音调、略快语速）→ 参照社区音色特征二次调参 → 专属音色克隆。

**授权约束**：克隆他人音色需本人明确授权；社区二创音色权利归属不清时不得直接克隆；商用前确认模型许可与音色来源；直播中按平台要求标识 AI 生成语音。

**后果**：首版音色是「接近」而不是「完全一致」；音色切换必须与人格版本绑定。

<a id="d-14"></a>
## D-14 首播采用单一主线目标

**状态**：已采纳 · 2026-11-02

**背景**：首播需要决定节目形态：自由生存、单一主线目标，还是分段节目单。

**选择**：首场设一个明确目标（例如盖一间带床和箱子的小屋），允许约 20% 的时间被弹幕打断。

**理由**：自由生存前 30 分钟大概率在砍树找羊，新观众会流失；单一目标让画面有进度感，也让承诺有落点；保留 20% 打断空间，观众才不会觉得评论没用。

**后果**：导演层需要「主线进度」概念，而不只是任务队列；打断过多时导演层要主动拉回主线；分段节目单留到 M4 再评估。

<a id="d-15"></a>
## D-15 寻路自研，Baritone 仅作对照

**状态**：已采纳 · 2026-11-02

**背景**：Baritone v1.17.0 支持 1.21.11 + Fabric，能力成熟，但采用 LGPL-3.0。项目许可证是 MIT OR Apache-2.0，且可能商业化。

**选择**：正式版使用自研 A*。开发期可单独安装 Baritone 做可达性与耗时对照，但不得进入发行包。

**理由**：自研没有许可传染风险；本项目只需要「走到某处、挖某类方块、返回」，不需要 Baritone 全功能；自研可把每 tick 预算、取消、进度汇报直接做进 Mod。

**后果**：寻路开发量增加，预计 1–2 周；复杂地形、跨维度、长距离导航需单独测试；若未来确认接受 LGPL 并完成合规流程，可重新评估，但不作为默认路径。
