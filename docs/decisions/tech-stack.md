# 技术选型

> 本文解释语言和框架取舍。系统结构见[架构总览](../reference/architecture.md)，决策索引见[决策记录](adr.md)。

## 负载假设

当前是单机、单直播间、单游戏实例：

- 评论峰值预计远低于千级每秒。
- 决策延迟预算是秒级，不是高频交易。
- 最紧的实时边界在 Minecraft tick，不在 Node 事件循环。

因此优先减少跨语言边界和维护成本，不为想象中的横向扩容提前引入复杂架构。

## 总览

| 层 | 选择 | 主因 |
| --- | --- | --- |
| 管理端 | React | 组件生态、类型共享、迭代快 |
| 桌面宿主 | Tauri 2 | 复用 React，包体和资源占用低于 Electron |
| 控制面与领域 | Node 22 + TypeScript | 共享契约、模型生态、单人项目维护成本低 |
| 数据 | SQLite WAL + FTS5 | 单机单写、可备份、无需服务端数据库 |
| 游戏 | Java 21 + Fabric | 客户端 Mod 和 Mixin 的唯一自然选择 |

## 为什么 React + Tauri

React 提供成熟的表单、列表和状态生态；类型可直接来自 `packages/contracts`。Tauri 只
承载窗口，不需要在 Rust 中复制业务逻辑，也比 Electron 更贴近原生桌面形态。

不选纯原生 UI 是因为无法共享 Web 类型和快速迭代；不选 Electron 是因为每个窗口绑定
完整 Chromium 运行时，包体和内存对常驻本机程序不友好。

## 为什么 Node + TypeScript

四个收益：

1. 前端、服务、契约使用同一语言和类型。
2. OpenAI 兼容流式、function calling 和 JSON 解析生态成熟。
3. 单机控制面以 I/O 编排为主，事件循环模型匹配。
4. zod 提供运行时边界校验，弥补外部输入不可信的问题。

代价也明确：单进程故障隔离弱、内存高于 Go、取消语义依赖 `AbortController`。这些用
有界队列、显式超时、loopback 鉴权、测试和进程拆分弥补。

## 为什么不用 Python

Python 适合模型脚本，但类型不能直接给 React，异步和打包分发成本高。控制面不是训练
或 notebook，不需要为此引入第二套后端语言。

## 为什么不用 Go

Go 的优势是真的：`context` 取消、goroutine、单二进制、低内存和高并发。但当前系统已
确定有 TypeScript 前端和 Java Mod，再加 Go 会变成三种语言、两套生成协议和更多边界。

Go 更合适的触发条件：

- 托管 3 台以上游戏实例。
- 评论持续超过 1000/秒。
- profiling 证明内核 p99 超过 200ms 且瓶颈在运行时。
- 需要对外发布单二进制 SDK。

当前都不成立。

## 为什么游戏侧是 Java

Fabric Mod 运行在 JVM 上，官方模板、Mixin 映射和社区示例以 Java 为主。Kotlin 会增加
编译和互操作层；单人维护 Mod 时，少一层抽象就是少一类映射错误。

## 为什么 SQLite

单机、单写者、单文件备份。WAL 支持运行时读写，FTS5 满足中文片段检索；迁移和约束可
以在内存库与文件库中验证。

不需要先引入 Postgres、Redis 或向量库。当记忆规模、检索方式或多进程写入真实变化时，
再演进存储接口。

## 反模式

- 不用“通用抽象”掩盖未验证的外部系统。
- 不把平台原文、prompt 或模型输出写进日志。
- 不在 Mod tick 线程做 I/O。
- 不让观众字符串进入系统提示。
- 不为假想负载提前引入服务网格、消息队列或多租户设计。
